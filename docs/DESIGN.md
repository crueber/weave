# Weave design contract (all contributors read this first)

Weave is a clean-room, behavior-compatible reimplementation of Planka (incl. Pro features) in Go + HTMX.
Reference behavior: the OSS clone at `$REF` and docs at planka.app. Read it for *behavior, field names, rules*;
do **not** copy its code, templates, CSS or assets (Planka licensing). Write original code. See docs/FEATURES.md for the ledger.

## Architecture
- Go 1.27, stdlib `net/http`, SQLite via `modernc.org/sqlite` (CGO-free, WAL). One replica only (in-process SSE hub).
- **One op registry** (`internal/ops`): every capability is `ops.Register[In,Out](Op{...}, fn)` in an `init()`.
  REST (`/api/v1`+Path), CLI (`weave <tag> <verb>`) and UI all use it. UI handlers (`internal/web`, `web.Route`) must mutate
  via `c.Do("op.name")` / `ops.Call` — never by writing SQL directly — so UI == REST == CLI.
  Reads for pages may also call ops (`ops.Typed[T]`) — prefer that; direct read SQL in pages only for page-specific joins.
- Input struct tags: `path:"id"` `query:"x"` `json:"x"` `required:"true"` `desc:"…"`; `*ops.File` for uploads.
  Every op sets `UI:` to its browser route/fragment ("POST /ui/cards/{id}/move") or `exempt:<reason>`. `go test ./internal/ops` enforces it.
- Responses: `{"item": …}` / `{"items": […]}`; errors `{"error":{"code","message"}}` via `ops.NotFound/Forbidden/Invalid/Conflict`.
- Naming: op `noun.verb` (`card.create`, `card.label.add`); CLI is `weave card create`, `weave card label-add`? NO: CLI verb is the op name after the first dot verbatim (`weave card label.add`). Path `/cards/{id}/labels`.
- Auth is OIDC-only (no local credentials). `ops.Authenticate` hook (auth domain) resolves cookie `weave_session` (created only by the OIDC callback), `Authorization: Bearer <token|apikey>`, `X-API-Key`. Permissions ONLY via `internal/authz` (`RequireBoard/RequireCard/RequireProject`, `BoardLevel`). Missing access ⇒ not_found (don't leak existence).
- Schema: `internal/db/migrations/0001_core.sql` defines all tables. **Do not edit 0001.** Add new migrations only in your reserved range (below), named `NNNN_desc.sql`. Never rewrite another range.
- **Card types removed** (migrations `0306` boards, `0401` cards): Planka's card `type` (project|story), `boards.default_card_type` and `boards.limit_card_types_to_default` are dropped (plain `ALTER TABLE ... DROP COLUMN`: no index, trigger, view or constraint used them, so data, indexes, the 0600 search triggers and foreign keys stay intact; `internal/db/migrate_test.go` upgrades a populated pre-0306 database). Labels do that job. Old inputs keep working: the op binder only reads the fields an op declares, so a legacy `type` on `card.create`/`card.update` or `defaultCardType`/`limitCardTypesToDefault` on `board.update` is accepted and ignored, and board imports read past those keys in old exports. Nothing returns them any more.
- IDs `db.NewID()`; times `db.Now()` (RFC3339 UTC); positions REAL, gap `db.PositionGap`(65536); insert at end = max+gap, between = midpoint, rebalance when gap<1.
- Writes: `e.DB.Tx(ctx, func(tx *sql.Tx) error)`. Keep tx short. No cross-package SQL on tables you don't own — call the owner's ops or exported Go funcs.
- Realtime: after a mutation `e.Hub.Publish(realtime.Event{Name:"card.updated", Room:"board:"+id, Data: …})`. Event names `<noun>.<created|updated|deleted|moved…>`. Webhooks tap the hub. Also write an `actions` row (activity log) + notifications where Planka does (notify domain exports `notify.Record(...)`; until it lands, call `ops.Call(e,"activity.record",…)`-free helper `ops.Emit` — see below).
- UI: server-rendered `html/template` in `internal/web/templates/` (embed). Files `layout.html` and `_*.html` are shared partials; each other file is a page defining `{{define "page"}}` plus optional named fragment blocks (`c.RenderBlock("board.html","list-col",data)`). Name your files with your domain prefix (`cards_*.html`, `_cards_*.html`) to avoid collisions. htmx 2 + tiny vanilla JS (`static/weave.js` has toast, modal `<dialog id=modal>`, native drag-drop `data-sortable`). No npm, no build step, no frameworks. Add CSS in your own `static/<domain>.css` linked from your pages' `<head>`-less content via `<link>` in the page template (layout loads weave.css only). Light/dark via CSS vars in weave.css. **Top-bar page slot**: `layout.html` has `{{block "topbar-page" .}}{{end}}` right after the brand; a page fills it with `{{define "topbar-page"}}{{with .Data}}...{{end}}{{end}}` in its own template file (same mechanism as `title`; `.` is the page data wrapper). The board pages (board, calendar, map, board settings) use it for breadcrumbs and the view switcher through the shared `_boards_topbar.html` partials (`boards_crumbs`, `boards_views`); cards supplies the board and project name to its pages via `boards.BoardCrumb`. The slot is rendered with the full layout only, so live updates (`#board-body` refetches) never touch it.
- Lazy sub-fragments: the card modal lazy-loads sections (`hx-get="/ui/cards/{id}/tasks" hx-trigger="load"`) so domains stay decoupled.
- Files: attachments/avatars/backgrounds under `$WEAVE_DATA_DIR/files/<kind>/…`; served only through authorized routes.
- Config: env (`internal/config`) + `config` table for UI-editable settings (smtp.*, oidc.*, branding.*). Secrets from env override DB.

## Quality bar
- `go vet ./... && go test ./...` green; each domain ships tests (table tests on ops via an in-memory env helper `internal/testutil`).
- CLI parity is automatic; keep `UI:` accurate. Document each op's `desc:` tags — agents read `weave schema`.
- No placeholder/TODO stubs in shipped ops. If a feature is infeasible, record it in docs/FEATURES.md as `partial` with reason.

## Agents and the event stream (0800 migration)

- **Agent prompts**: `internal/agentprompt` (leaf package: plain `Data` in, text out, golden tests) is the single source of the prompt text; the
  `agent.prompt` op (boards domain, `agentprompt_op.go`; scopes general|project|board|list|runner|workorder; View on the object, general/runner carry no object data,
  a work order's card must be on the list's board) feeds the browser dialog, REST, `weave agent prompt` and the generated skill reference `prompts.md`.
  The general, project, board and runner texts are **editable plain text with `{tokens}`** (`defaults/*.txt` are the built-ins); `Expand` is one pass that only
  replaces the scope's known tokens with pre-rendered strings (never `text/template` on user text; unknown tokens and `{{` stay literal, values are not rescanned).
  The **shared blocks** (`{instance}` `{connect}` `{keynote}` `{concepts}` `{questionnaire}` `{etiquette}` `{security}` `{readmore}`) are editable plain text too
  (`blocks/*.txt`, `blocks.go`; admin only, global: config `agentblock.<name>` via `notify.AgentBlocks`, filled into `Data.Blocks` for every scope). A block may use
  data tokens only (`{server}` `{install_base}`; connect also `{install}` `{install_skill}`, the two install lines, which are blocks of their own), never another
  prompt block, so nothing recurses. The old template conditionals are Go decisions: `{etiquette}` picks `etiquette` or `etiquette_compact`, `{concepts}` is empty
  when Compact, the install lines are empty with the install steps off (a line holding only an empty token is dropped; a whole-line token's expansion is indented
  like the token). The column prompt and the work order stay Go templates over `Data` (list.tmpl gets the rendered blocks as `.Block.<name>`), and `{columns}`,
  `{boards}`, `{board_line}` stay generated, so `{columns}` always renders fenced, cut briefs. `AgentPromptOut.customBlocks` names the customised blocks a prompt
  used (the dialog notes them, linking admins to the Blocks tab); `agent.prompt.preview` (admin) renders a prompt or block with the example data.
  Resolution in `BuildPrompt` (`AgentPromptOut.source`): board = `boards.agent_prompt` (migration 0305) -> config `agentprompt.board` -> built-in; project =
  `projects.agent_prompt` (0201) -> `agentprompt.project` -> built-in; general/runner = `agentprompt.general|runner` -> built-in; no board -> project fallback.
  Writes: `board.update agentPrompt` (board Manage, like sharing), `project.update agentPrompt` (project Manage), `config.update agentprompt.*|agentblock.*` (admin; UI
  Admin console > Agent prompts, `notify_agentprompts.html`, two tabs `?tab=prompts|blocks` of expandable editors; a save redraws only its editor). `agentprompt.Normalize` strips control characters, caps at 20000 bytes and stores text equal to the
  default that applies as empty. Board text travels with export/import and templates (`impBoard.AgentPrompt`, cleaned on import); public board views blank it.
  Prompts never carry a key; column descriptions are fenced and neutralised (capped at 600 chars in the board prompt). `weave agent run --outbox` is the
  token-free runner mode (see docs/CLI.md).
AI agents attach to board **lists** and take work through the board; humans see who listens where and agents never double-claim.
- **Agent accounts** (`internal/domain/auth/agents.go`): non-SSO `users` rows with `is_agent=1`, synthetic email `agent-<id>@agents.invalid`, no login (the OIDC callback and the session lookup skip them), API key only. Ops `agent.create|list|update|rotateKey|delete|access`, authorized in `internal/authz/agents.go` (see "Owner-created agents" below; `agent.access` goes through the `board.member.*` ops; `commenter` = viewer + canComment). `ops.Principal.IsAgent` feeds `actor.isAgent`. Agents show a robot badge (`auth_robot` partial, `agents.css`). `auth.whoami` returns user, role, isAgent and boards with role.
- **Owner-created agents** (migration 0110 `users.created_by`): an agent is a service account a *person* creates for boards they
  manage. `agent.create` needs `RequireBoard(Manage)` on every `boardIds` entry (required for non-admins; an admin may create an account
  with no boards, and gets no board Manage from the admin role), records the creator, and always gives non-admin creations role `boardUser` (only admins pick worker/guest, on create or
  `agent.update`). Grants are board memberships of role editor | viewer | commenter only (never project-wide, never admin, never a board
  owner role, so an agent never manages members); `agent.access` grant needs Manage on the *target* board (a manager may invite an existing
  agent onto their own board), revoke needs Manage on it or being the agent's creator (never the admin role; the creator's revoke on a board they do not
  manage runs `board.member.remove` as the agent leaving the board, so the boards domain still does the write). `authz.CanManageAgent`
  (rename, deactivate, rotate key, delete) = a system admin (ACCOUNT control), the creator, or a caller with Manage on every board the agent holds (at least one);
  `authz.CanSeeAgent` (listing) = admin, creator, or Manage on at least one of its boards. `agent.list` (optional `boardId`, needs Manage)
  returns those agents with `boards` filtered to the ones the caller manages (admins included: the admin role names no other board),
  `boardCount` (the total, so an admin sees how many without seeing which), `createdBy`,
  `createdByName` and a per-caller `canManage`. Agent principals are refused every `agent.*` op and every `webhook.*` op
  (forbidden or not_found). `WEAVE_AGENTS_PER_USER` (default 50, 0 = off; admins exempt) caps agents per creator. Keys are returned once and never logged.
  UI: Board settings > Agents lazy-loads `GET /ui/boards/{boardId}/agents` (auth domain, `auth_board_agents.html`, the `.adm-kit` pieces of
  `admin.css`: create for this board with the one-time key, access per agent, remove access, rename, rotate, deactivate, delete, add one of
  your agents); `/admin/agents` is account management for admins (name, creator, status, key, board count; board names and the board
  picker only for boards the admin manages, no links into boards); the Connect-an-agent dialog's Board and Runner tabs show "Create an agent for this board"
  to a board manager when no agent account has access.
- **Durable events** (`internal/events`): every `ops.Emit` already ends in `notify.Record`; its default ActionWriter now also stores, on the `actions` row, `seq` (allocated inside the INSERT as `MAX(seq)+1` under SQLite's write lock, so seq order = commit order, ids never reused), `etype`, `list_id`, `from_list_id`, `to_list_id` and the envelope JSON (without id). Emission is always after the domain transaction committed. An event about a card on several boards is stored once per board with a shared `origin` (see "Placements", events). The public event id is `seq` zero-padded to 12 digits. The card snapshot is taken at write time (hook `events.Snapshot`, installed by cards). `ops.Event.Kind` overrides the stream type (archive/restore are realtime-named `card.moved` but stream `card.archived|restored`). Bulk list ops (move-cards, archive/trash a list, clear trash) emit one event per card.
- **SSE** (`internal/server/sse_events.go`): `GET /events` with any of `boards lists types since heartbeat agent` (or a `Last-Event-ID` header) is an envelope stream; plain `rooms=` stays the legacy hub stream byte for byte. The handler *tails the database* (`events.Query`, `seq > cursor`) and uses `Hub.Tick()` only as a wake-up (plus a 2 s poll), so replay and live are one path: same ids, ordered, no gaps or duplicates, and nothing is lost if a consumer is slow. Access is re-checked per board (10 s cache); unviewable ids behave like unknown ones. Credentials and board access are re-checked every 3 s on open streams: rotating/deactivating a key, deleting an agent or revoking access ends the stream (and clears its listener registration). Agent keys are rejected when presented as a session cookie. Payloads older than `WEAVE_EVENT_RETENTION_DAYS` (default 90, minimum 30) are dropped by a background job; the activity rows stay.
- **Browser realtime (who listens to what)**: a tab holds exactly ONE legacy `rooms=` stream, owned by `static/notify_live.js` (loaded by
  `layout.html` for signed-in users). The server always adds the caller's private room `user:<me>` (`authz.RoomAllowed` refuses anyone
  else's), so `notification` events (`data.action` = `create` with the recipient's own row, or `update|read|read_all` after mark-read;
  published by notify only to `user:<recipient>`) and the `project.*`/`projectManager.*` user-room events reach every page. Page scripts
  never open their own EventSource: they add rooms and listeners through `window.WeaveLive` (`setRooms(owner, rooms)` replaces that
  owner's rooms and reconnects once; `on(name, fn)`; `on('reconnect')` after a dropped stream comes back). The board page registers
  `board:<id>` synchronously before the bus connects (both scripts are `defer`; the bus starts after DOMContentLoaded), so a board tab
  opens one stream, as before this bus existed. The bell's state is the server-rendered `#notif-badge` fragment: any change to it
  (first load, refetch, the out-of-band swap after "Mark read") drives the lit class, aria-label and "(n) " title prefix. Rooms have no
  replay, so the badge is refetched (debounced, `X-Weave-Background`) on every `notification` event, after a reconnect, on becoming
  visible and every 5 min; a stream that closes (401, `429 too_many_streams`) or misses three reconnects falls back to 60 s polling
  (visible tabs) with 5 s..10 min backoff for new attempts. A tab hidden for 2 min with no page rooms parks its stream (frees the
  per-user slot and the browser's per-origin HTTP/1.1 connection) and polls the badge once a minute until it is visible again.
  The legacy stream re-authenticates every 30 s (`legacyRecheck`): sign-out, idle auto-logout (the stream never refreshes
  `last_used_at`), deactivation or a rotated key end it. Tests: `internal/server/notify_stream_test.go`; browser:
  `scripts/notify-live-smoke.mjs`.
- **Listener presence** (`realtime.Listeners`): a stream with `lists=` registers (label from `agent=` or the user name) for the life of the connection; `list.listeners` / `board.listeners` read it; `listener.joined|left` go to the board room (ephemeral, not stored) and the board page re-renders the robot indicator in list headers.
- **Board templates**: two sources, one creation path. Built-ins are JSON manifests embedded in `internal/domain/boards/templates/*.json` (`builtin:<slug>` ids, a `weave-board` document plus gallery metadata; the manifest test enforces preset colours, no absolute dates/people/comments, sane WIP and offsets); published templates are boards flagged `is_template` (migration 0304: `template_visibility` private|group|public, `template_group_id`, `template_publisher_id`, `template_published_at`). Both become an `impBoard` and are created by `createImported` (shared with file import), so label reuse for project-wide labels, colour validation and limits are identical. Visibility is `authz.TemplateVisible` (anyone with access to the board, the publisher, then the visibility rule; the admin role adds nothing). Cards carry `dueOffsetDays` (days from creation); a published template derives offsets from `template_published_at`. Custom fields travel through `boards.ExportCustomFields/ImportCustomFields`, hooks installed by cardextras (flattening base-group groups; card-level groups only with cards). Admins hide built-ins with config `templates.hidden`.
- **Applying a template to an existing board** (`board.template.apply`, `boards/templateapply.go`, board **Manage**, checked before the template so an outsider always gets "board not found"; the template goes through `loadTemplate`, so visibility and hidden built-ins apply; a board cannot be its own template). `writeImport` is split into reusable parts (`writeImportSettings`, `writeImportLabels`, `writeLists`, `writeCards`, the custom-field hook) that import and `board.instantiate` compose exactly as before; the apply composes `writeLists`/`writeCards`/the hook with its own label merge and settings writer. In ONE transaction (`BEGIN IMMEDIATE`):
  columns: the template's active/closing columns at positions 1..n, the board's existing finite columns renumbered after them in their order;
  target: the first template column that does not close cards (a closing first column is skipped with a warning; a template whose every column closes cards is refused);
  cards: every non-draft, non-template card in an active/closing column, in board order (old column position, card position), appended to the target (`prev_list_id` = old column, `list_changed_at` = now, one `UPDATE ... CASE` per 500), landed with **`boards.LandedKeepClosed`** (closed cards stay closed, no archive-after pass); claims move with their cards; archive and trash untouched;
  **old columns removed (decision, maintainer: "it should remove the old columns after the cards are moved")**: with `removeOldColumns` (a `*bool`, nil = **true** for the API, the CLI and the UI tick box "Remove the old columns (they will be empty)"; `false` keeps them, emptied, on the right, the earlier behaviour) `removeOldColumns()` deletes the old active/closed columns in the same transaction, after the move. Safety rules: `cards.list_id` and `list_subscriptions.list_id` are `ON DELETE CASCADE`, so (1) inbox drafts and card templates, which park on a real column (a draft on the board's first active list), are re-pointed to the target (appended, still `is_draft`/`is_template`, so still in the Inbox and the project's card templates and still hidden from the column) BEFORE the delete; (2) then `SELECT COUNT(*) FROM cards WHERE list_id IN (old)` (no board filter, like the cascade) must be 0, else the apply fails and rolls back (never a silent cascade); (3) archive/trash lists are not touched; `prev_list_id` has no foreign key, so archived/trashed cards (and the moved cards) keep naming a deleted column and `card.restore` / un-closing fall back to the board's first active list, which is the target; a recurrence `listId` naming an old column falls back to the card's own column; (4) column watches cascade away, and the old columns' own settings (closing, WIP, archive-after, description) and their column Activity sheet go with them (the events stay in `actions`; each card's feed keeps its history). The preview (`columnsRemoved`, `columnsKept` empty, no duplicate-name warning) warns with the old columns' settings, the number of column watchers, live listeners (`realtime.Listeners.ForList`) and the archived/trashed cards that came from them. Agents listening on an old column see each card's `card.moved` (from the column), then `list.deleted`; their stream stays open but silent and a reconnect with only that list id is not_found (documented in docs/AGENTS.md and the skill). Because the old columns are gone, `prev_list_id` no longer suffices to rebuild a revert (the export is the undo);
  labels: only added. Board-visible labels (plus project labels when `use_project_labels`) match by trimmed, case-insensitive name; unnamed labels by resolved colour; a match is reused as it is (never renamed, recoloured, regrouped, deleted). New board labels are appended and go into a board label group of the same name, else a new group from the template (created only when one of its labels is added); with project-wide labels new labels are project labels and need project Manage (skipped with a warning otherwise; today board Manage implies it);
  custom fields: template board-level groups whose name (trimmed, case-insensitive) exists on the board (`ExportCustomFields`, incl. flattened base groups) are skipped whole; the rest are appended after the board's groups (`importBoardFields` starts after the board's highest position; 0 on a new board); card-level groups only with sample cards;
  settings: only with `applySettings` (colour and view only when the template has them, card colouring, the flags); **never the agent prompt**;
  sample cards: only with `includeSampleCards`, into their template columns after any moved cards, landed with `Landed`.
  **Archive after N on the target (decision)**: an apply never archives the user's cards. If the cards landing in the target (moved plus its sample cards) exceed the template's N, the target is created **without** the setting and a warning names N and the count (keeping it would make the next ordinary landing archive the whole excess at once); otherwise the setting is kept. Other template columns keep theirs (they only receive sample cards).
  `dryRun` runs the same function and rolls the transaction back (sentinel error), so preview and apply report identical numbers; a real run requires `confirm=true` (validation error otherwise). No automatic undo: the confirm links the JSON export (and names the columns it removes). Events after commit: `list.created` per new column (`auto: "applyTemplate"`), one quiet `card.moved` per moved card (`auto: "applyTemplate"`, `templateId`, `quiet: true`), one quiet `list.deleted` per removed column after the moves (`auto: "applyTemplate"`, `templateId`, `quiet: true`), quiet `card.created` per sample card, `label.created` per added label, `EmitAutoArchived` for sample cards, then one `board.updated` summary (type `boardUpdate`, data `appliedTemplate`, `templateId`, `columnsAdded`, `columnsRemoved`, `cardsMoved`, `targetListId`, `labelsAdded`, `sampleCards`, `settings`; Activity: "... moved 7 cards, removed 3 old columns"), which is the board Activity row and the live refresh of open boards. The board Activity feed (`activity.board`) leaves quiet per-card events out (the card's own feed keeps them). UI: Board settings > Templates & export row (managers only) opens `GET /ui/boards/{id}/apply-template`, the gallery with `BoardID` (`?boardId=` on the grid/preview routes, checked with board Manage), whose preview ends in "Preview changes" (the op's UI route with `dryRun`), rendering `boards_tpl_apply`; ticking an option re-previews; "Apply template" posts `confirm=true` and redirects with a toast carried across the navigation (`HX-Trigger: toastNext`, `weave.js` sessionStorage). MCP: not in `mcpDestructive` (the op's own `confirm` is the gate, so a dry run needs no `weave_call` confirm).
- **Column briefs**: `lists.description` (migration 0302) is the column's brief — what a card that lands there asks for. It travels in `List` (so `board.tree`, `list.list`, export/import and board templates carry it) and is the first thing the agent skill tells an agent to read: a column's name *and* description are the request. The **column sheet** (`GET /ui/lists/{id}` fragment into `#modal`; `GET /lists/{id}` is the shareable URL: the board page with the sheet opened by `static/boards_listsheet.js`; both View level, archive/trash lists are not_found) is the configuration view of one column, built from the card sheet's own `.cm-*` classes (`.ls.cm`; the dialog sizing in `cards_modal.css` lists `dialog#modal:has(.ls)` next to the card sheet; the sheet has none of the card sheet's ids/data hooks, and its popovers, section toggles and description editor are handled by `boards_listsheet.js`): top bar (breadcrumb with a column switcher, prev/next column, `...` menu with archive/delete), an inline-editable title, a markdown description (rendered by the cards renderer through the global `cards_md` template func; stored raw because agents read it), a Properties rail (Auto-close and WIP limit edit in popovers; cards, created, updated read-only), Sort / Move all cards, a collapsible **Agent prompt** (editors only; collapsed by default; the older standalone `GET /ui/boards/{boardId}/lists/{listId}/agent-prompt` fragment still exists). Its **Activity** section is the `list.activity` op (View level; newest first, paged by event id): column-scoped rows of the durable event stream (`events.Recent` over `actions.list_id/from_list_id/to_list_id`: cards created in, moved in or out, archived, cleared; column created/updated/sorted), so it only reaches back as far as the event retention window. Mutations post to the normal list UI routes; one history entry per sheet session, closing goes back, delete rewrites the entry to the board URL, and the single `popstate` listener in `cards_ui.js` dispatches `/cards/` vs `/lists/`. **Soft WIP limit**: `lists.wip_limit` (migration 0303, NULL = none; API/UI `wipLimit` 1-10000, `0` or an empty form value clears it) is advisory: the header shows `cards/limit` (cards = the column's unfiltered total) with an over-limit state (flag glyph + text/aria-label, not colour alone) and nothing is ever blocked; it travels with board duplicate/templates and export/import (out-of-range values in files are dropped). Hard enforcement would have to live in the cards domain (`card.create/move/next/claim`). The column menu's older **Agent prompt** route produces a plain-text brief to paste into an agent: server URL and API-key login, install line for a missing CLI/skill (`WEAVE_AGENT_INSTALL_URL`), the column with its description, and one `--list` line per other column so the operator can add columns by editing the text (`boards.AgentPrompt`). The prompt never contains a key: the operator pastes it into the editable text before copying (secrets stay write-only).
- **Claims** (`internal/domain/cards/claim.go`): `claimed_by/claimed_until/claim_note` on `cards`. `card.claim|release|renew|next`. One guarded write in an IMMEDIATE transaction (`claimInTx`) makes exactly one concurrent claimer win (others get 409). Expired leases read as unclaimed everywhere; a 20 s sweeper emits `card.released` (reason `lease_expired`), and a takeover of a lapsed lease reports the lapse too. Claiming needs Edit on the board (viewer/commenter agents can listen but not claim). The caller becomes a card member.
- **Context-efficient reads**: `board.tree`, `card.get?full=true` (composed from the cardextras ops via `ops.CallMap`), `card.list` filters (`listId labelId memberId claimed q limit cursor`); `board.tree`, `card.claim`/`card.next` and event envelopes share the compact `events.CardSnap` (`card.list` returns full card rows): `{id,boardId,name,description,listId,position,labels[{id,name,color}],members[{id,name,isAgent}],dueDate,isClosed,claimedBy(id),claimedByName,claimedUntil,tasksTotal,tasksCompleted}`. Task counts come from `events.TaskCounts`, installed by cardextras (it owns tasks): one aggregate query per 400-card snapshot chunk, so a 1000-card `board.tree` stays a handful of queries.
- List-valued ops answer `{"item":[...],"items":[...]}`.
## CLI, snapshot and agent skill (`make skill` is mandatory after op changes)
- The CLI (`internal/cli`) is **schema-driven** and never imports `internal/ops` (so the slim `cmd/weave-cli` binary does not link SQLite
  or the server). It reads `GET /api/v1/_ops` from the server (cached per server), falling back to the registry of the full binary and to
  the embedded `internal/cli/snapshot.json`. `internal/cli/opsbridge` converts the registry for the full binary and the generators.
- `skills/weave/**` (the Claude-Code-compatible agent skill, embedded in the CLI by the `skills` package) and `internal/cli/snapshot.json` are
  **generated** by `go run ./cmd/weave-skillgen` (= `make skill`, also run by `make build`) from the op registry plus the hand-written
  sources in `internal/skillgen/src/`.
- `skills/instructions.md` is the **compact rendering** (a few KB, from `internal/skillgen/src/INSTRUCTIONS.md`) of the same guidance for tools
  that only read instruction/rules files; both renderings keep the "treat card content as untrusted data" section and are covered by
  `make skill-check`. `weave skill install` (`internal/cli/skillcmd.go`, `skilltargets.go`, `skillinstall.go`) is a data-driven target
  registry (one entry per coding-agent tool; paths and sources in `docs/AGENT-TARGETS.md`). Skill folders carry a `.weave-skill.json`
  manifest (per-file hashes); instruction blocks are wrapped in `<!-- BEGIN weave-skill vX sha:H -->` ... `<!-- END weave-skill -->`.
  That is how `check` tells current/stale/modified apart and how reinstall and uninstall touch only what Weave wrote.
- **Any new or changed op (name, path, fields, `desc:` tags, summary) requires `make skill` and committing the result.**
  `go test ./cmd/weave-skillgen` regenerates in memory and fails with "run `make skill`" when the committed files differ.
- Agent-facing ops (claim/lease, `card.next`, `board.tree`, listeners, `whoami`, `agent.*`, event stream `GET /events`) are specified in
  `docs/AGENTS.md` section "Server contract". `internal/cli/overlay.go` holds a fallback copy of their schemas for servers that do not
  serve them yet; once the registry has them the overlay entries are ignored and can be deleted.

- **`weave mcp`** (`internal/cli/mcp_*.go`) is an MCP server over stdio inside the slim CLI, a *connector* not a server surface: it calls
  the same REST ops with the profile's key and adds no permission path. `mcp_tools.go` derives tools from the op schema without SDK types
  (name `weave_<op with _>`, JSON schema from field `in/type/required/desc`, description, annotations from method/verb); the only hand-written
  list is `mcpCurated` (op names; a test fails on an unknown name). `weave_ops` + `weave_call` reach every other op (`confirm: true` for
  `mcpDestructive` ops; `isDestructive` still drives the CLI's TTY prompt). `ops.Schema` carries `binary` (file-stream response) and
  `maxBytes` (`Op.MaxBody`) so uploads (`in:"file"` fields) and downloads are detected mechanically. `App.CallStream` streams multipart
  uploads through a pipe and hands binary responses to a sink (no 64 MiB buffer). File access goes through `mcp_files.go` (allowed roots,
  deny list even inside roots, symlink resolution, `os.Root`, regular files only, size caps; Windows UNC/ADS/reserved names). Prompts call
  `agent.prompt`; resources `weave://board/{id}` (`board.tree` summary) and `weave://card/{id}` (`card.get`). Pull only: no SSE over MCP.
  The key never reaches tool output, prompts, logs, errors or written client configs. Official SDK `github.com/modelcontextprotocol/go-sdk`.

## Placements (`card_placements`, migration 0404)
One card (not a mirror, not a copy) may sit on several boards so different teams follow it in their own columns. It was built in phases (1 schema, triggers and authz helper; 2 read paths; 3 event fan-out, notifications and webhooks; 4 write ops `card.place`, `card.unplace`, `card.placements`; 5 the UI, read half then write half, below). API, CLI, MCP and the UI all have it.
- **Model**: `card_placements(card_id, board_id, list_id, position, prev_list_id, list_changed_at, is_home, placed_by, placed_at)`, `PRIMARY KEY(card_id, board_id)` (never twice on one board), `WITHOUT ROWID`; `cp_home` (unique: at most one home per card), `cp_list(list_id, position)` (column order), `cp_board(board_id)`. It holds **every** placement, the home included. `card_id`, `board_id` and `list_id` cascade on delete (a card, board or column deleted takes its placements; nothing is orphaned), `placed_by` is set null. The migration backfilled one home row per card (drafts and card templates included; plain `INSERT`, so a row that cannot be written fails the upgrade instead of leaving a card without a home).
- **Per placement**: the board, the column, the position, the previous column (restore target) and `list_changed_at` (column age, archive-after order). **Per card**: everything else, **including the closed state** (`cards.is_closed` is not a placement column; maintainer decision) and archive/trash as *actions* (see the decisions below).
- **The mirror**: `cards.board_id/list_id/position/prev_list_id/list_changed_at` stay as a read-only mirror of the HOME placement, so every reader that has not been converted (and the previous binary) sees the home, which is right for single-placement cards. Triggers keep it:
  - `cp_home_ai` (AFTER INSERT ON cards): every card insert (create, import, instantiate, duplicate, from-template, recurrence, drafts) gets its home placement.
  - `cp_home_mirror` (AFTER UPDATE OF list_id, position, prev_list_id, list_changed_at ON card_placements, when the row was and is home on the same board): copies those four columns. It never names `cards.board_id`, because the 0600 search trigger `notify_card_au` fires on `UPDATE OF board_id` even when the value is unchanged: a reorder, `list.sort`, rebalance or same-board move never touches the search index (tested with a delete log on `search_map`).
  - `cp_home_rehome` (AFTER UPDATE OF board_id, is_home, when the row is home and either just became home or changed board): sets the board and the four columns in one statement (cross-board `card.move`, draft publish onto another board, a future re-home); `notify_card_au` then reindexes the card and its comments under the new board. The two triggers are mutually exclusive by the row's OLD/NEW values.
  - `cards_placement_guard` (BEFORE UPDATE OF those five columns ON cards): aborts with "... write the placement" unless the new row equals the home placement. The mirror passes (the placement already holds the values); any other writer fails loudly instead of drifting. SQLite runs these nested triggers whatever `recursive_triggers` says (it only stops a trigger re-firing itself); `internal/db/migrate_placements_test.go` proves the chain under modernc with the default setting.
- **Rule for writers: write the placement, never the mirrored columns on `cards`.** Converted: `doMove` (card.move, archive/restore/close, claim/release/`card.next` moves, drops), `positionFor`/`endPos`/`rebalance` (cards), draft publish, `list.sort`, `boards.moveAll` (`list.moveCards`, archiving/deleting a column), `applyArchive` (archive-after), `board.template.apply` (the card move and parking drafts before removing old columns), and the drop/quick-add positions (`boards.PlaceCardBetween`; the generic `PlaceBetween`/`Rebalance` take a table name and must never be given `cards`). `updated_at`, `is_draft`, `is_closed` and every other card field are still written on `cards`, in the same transaction. The boards domain writes `card_placements` directly (its writers live there and cards imports boards, the precedent of `boards.Landed` writing `cards.is_closed`). A repo test (`internal/db/placements_scan_test.go`) fails on any Go file that updates a mirrored column of `cards` or hands `"cards"` to the generic position helpers (allowlist: the trigger tests), and `testutil.CheckPlacements` (run by every `testutil.Env` at cleanup, explicitly by tests that open their own database) asserts: one placement per (card, board), exactly one home per card, home = the cards columns, each placement's column on the placement's board, drafts and card templates never placed twice.
- **Authorization** (`internal/authz/placements.go`): `CardAccessFor(e, cardID, boardHint)` reads the placements in one query and the levels with `BoardLevel` (one placement) or `BoardLevels` (several; constant queries): `Level` = the maximum over the placements the caller can view, `Boards` = the viewable placements only (hidden ones are never counted or named), `HomeBoardID` = "" when the home is not viewable, `BoardID` = the context (the hint if viewable, else the home if viewable, else the highest level, then the oldest placement). `RequireCard` (signature kept, returns the context board, same error texts as before), `RequireCardEdit` and `Card` (caps) are thin wrappers. The worker rule stays narrow: `CardAccess.WorkerMember` is read only by `RequireCardEdit`/`Card.CanEdit`, never folded into `Level` (claims and the cardextras ops do not follow it). `RequireCardOn(e, cardID, boardID, min)` is for placement-scoped actions; `CardViewers` (user -> viewable placement boards, one query) and `CardLevels` (bulk) are for the planner, search and dashboard phases. `BoardOfCard` is documented as the HOME board, not an access check. The cardextras helpers that resolved a card's board themselves (tasks, attachments incl. download, time entries, custom-field rows) now call `RequireCard`. With one placement every answer equals the old single-board check (`TestSinglePlacementAccessUnchanged` compares against the old implementation for every persona; the persona, capability-matrix and sweep tests are unchanged).
- **Decisions (maintainer, amending the plan)**: (1) closed is per CARD; (2) archive and delete (trash) are CARD actions affecting every board the card is on, each board's placement going to that board's archive/trash list; taking a card off one board is "Remove from board" (`card.unplace`), there is no per-board delete and no `everywhere` flag, and card-level actions need Edit on any placement the caller can see; (3) no special rule for public boards; (4) cross-project placement is allowed.
- **Read paths (phase 2)**: every board reader reads `card_placements p JOIN cards c ON c.id=p.card_id WHERE p.board_id=?` (or `p.list_id=?`) and takes the column and position from `p`, so a card shows **once on every board it is on** (one placement per card and board) and never twice on one: tiles (`loadTilesOnly`, hence the WIP header and column counters, the public board and the quick-edit tiles), `board.tree`, `board.stats`, `card.list`, `card.calendar`, `card.map`, the list sheet count, the quick-add first card, the drop check, the template sample-card count, `board.export` (what is on the board, with that board's columns and labels), the HTML/PDF `export.board`/`export.card`, the board field export, the linked-card picker and `attachment.media`. Closed stays per card (`cards.is_closed`), so Done counts and `includeClosed` read the card. Child rows (labels, members, tasks, comments, fields) join the placement too, never `cards.board_id`.
- **Per-board labels**: `card_labels` stays card-level, but a board shows only its own vocabulary: `db.LabelOnBoard(l, b)` = `l.board_id = b OR l.project_id = b's project`. Readers deliberately ignore `use_project_labels` (project labels already on cards stay visible after it is switched off, as before); writes keep `labelAllowed`. Applied in tiles, snapshots (`board.tree`, events), `card.get`/`card.list` `labelIds`, `card.options`, the calendar colours, both exports and the `card.list` label filter.
- **Context board**: a card read names ONE board, the context: `CardAccessFor(e, card, hint).BoardID` (the hint when placed there and viewable, else the home when viewable, else the highest level, then the oldest placement). `card.get`, `card.options` and `customfieldgroup.list` take an optional `boardId` hint; `loadCardOn(e, q, card, board)` reads that placement (`boardId/listId/position/prevListId/listChangedAt`) and its labels; the card-field writes (`card.update`, labels, members, location, cover, recurrence, claim/renew/release without a move) answer with the card on the caller's context board; `card.move` reads and moves the placement `resolveMove` picks (`doMove` loads it with `loadCardOn(srcBoard)` and answers on the destination board: a caller working on another board never sees or emits the home's column); `card.archive`/`card.restore` move every placement and describe the context one in their event, `card.close` moves the context placement (see "Write ops" below). `card.get` adds `homeBoardId` (empty when the home is hidden), `placements[]` (board, project and column names, `isHome`; viewable boards only) and `alsoOnBoards`; these per-viewer fields are cleared before any event, activity or webhook payload. The share token shows only with Edit on the home. Board-wide custom-field groups show on their own board only (card-level groups everywhere); a value write on a board-wide group needs the card placed on that board and Edit there (`RequireCardOn`). The quick-edit tile routes take `?board=` (or a `board` form field) as the hint. `events.SnapshotOn(e, card, board)` / `SnapshotsOn` snapshot a card on one board (nil when not placed there); `events.Build` uses it for the event's board, `Snapshot`/`Snapshots` keep meaning the home.
- **Bulk readers** (search, dashboard, Settings > Watching) use `authz.CardAccesses(e, ids, hint)` (one placements query plus one `BoardLevels`; the same decision as `CardAccessFor`, tested against it): one row per card, shown on its context board; hidden placements are never named. Search keeps ONE index row per card and comment (the home); the `boardId` filter also matches cards placed on that board and their comments, and then keeps only hits the caller can see ON that board (so the filter never reveals a placement on a hidden board). The "also on N other boards" data (`Tile.AlsoOn`, `alsoOnBoards` in `board.tree`, `card.list` and `card.get`) counts only other boards the viewer can see (`authz.AlsoOn`: one placements query plus `BoardLevels`). Every converted reader keeps a constant query count (`TestPlacedReadsQueryCountIsConstant`, three placements per card).
- **Events (phase 3, migration `0801_action_origin`: `actions.origin_id` + partial index)**: ONE logical event, ONE `actions` row per board it concerns. `notify.Record` decides the scope (`eventScopeOf`): `ops.Event.Boards` when the writer listed the boards, else `[ev.BoardID]` for a **placement event** (`events.PlacementScoped`), else every board the card is on (hook `events.Placements`, installed by cards; the event's board first, then home, then by `placed_at`). `perBoard` builds one copy per board: the first (origin) row is written as before with the pre-generated `actionId`; every other row gets its own id, `origin_id` = the origin's id, its own `seq`, `board_id`, `list_id` (from that board's snapshot) and envelope. Every copy's `data.card` is that board's view (`events.CardOn`, installed by cards: that placement's column and position, that board's labels, no per-viewer field and **no share token**); on a non-origin copy `data.boardId` is that board and every column or board id of another board (`listId/fromListId/toListId` checked with one `events.ListBoards` query, `fromBoardId/movedToBoardId`) is dropped, so a card-level archive on A tells B "card.archived" with B's own column and no A column. All copies share `actionAt` (one `created_at`/`at`), and every envelope carries **`origin`** (`Envelope.Origin`: the origin row's id; also on single-board events). The writer (`ActionWriter func(*ops.Env, ops.Event) bool`) writes no fan-out copy when the origin row fails. `events.Query`, the SSE access checks (per row's `board_id`), `events.Recent` (column activity), `board.stats` and `lists=` filters are unchanged: an agent streaming boards A and B gets ONE envelope per board with the same `origin` and dedupes by it.
  - **Scope table.** Placement events, scope `[ev.BoardID]`: `cardCreate`; every `cardMove` that moves ONE placement: `card.move` within or between the columns of one board (an archive or trash column included), a cross-board relocation (`fromBoardId` differs: the source half `card.deleted` is written with `Boards=[source]`), the claim/release moves, `list.moveCards`/`list.archive`/`list.delete` (that board's placements) and the **archive-after rule** (quiet `card.archived`, data `auto:"archiveAfter"`, also written with `Boards=[board]`); `cardPlace`/`cardUnplace` (stream `card.placed`/`card.unplaced`, webhooks `cardPlacementCreate`/`cardPlacementDelete`; written with `Boards=[that board]`, also by `list.clear`). Card-level events, scope = every board the card is on: comments, `card.updated` (fields, due date, `isClosed`, `home`/`placements`), members, claims and releases (also the sweeper and agent deletion), tasks, attachments, time, card-level custom fields, **`card.archive` (archive or trash) and `card.restore`**: they move every placement and mark their `cardMove` with the routing key **`events.CardLevel`** (`cardLevel: true`, stripped from stored data, publishes, envelopes and webhook payloads), so the event is card-level by that key and not by its kind (an archive whose context placement was already archived still reaches the others), and carry **`events.PlacementLists`** (board -> [from, to] column of that board's placement, hidden like `CardLevel`) so each board's copy names its OWN `fromListId`/`toListId` (a `lists=` filter or the column activity of the column a placement left on another board sees the move); and **delete** (`card.delete` and `list.clear` read the boards BEFORE the write and pass `Boards`; every room gets `card.deleted` with no snapshot). Narrower by the writer's `Boards`: `card.label.added|removed` reach only the boards that show the label (`db.LabelOnBoard`), values and rows of a **board-wide** custom-field group only that board (`groupScope`). A move into or out of a closing column is a placement event for the stream but a card-level `closeCard`/`reopenCard` for notifications (closed is per card); a landing that closes or re-opens a card that is on several boards (a move, a placement, a restore, `list.moveCards`) also emits one quiet `card.updated` `changed:["isClosed"]` (`boards.EmitClosedElsewhere`), card-level, so every board's tile shows the state. Archiving a closed card is a move (archive and trash keep the closed state), never a `reopenCard`.
  - **Legacy hub**: `Publish` once per `board:<id>` room in scope, each with that board's own data (an event with a custom room, e.g. `global`, publishes once). A placement event (also one written with an explicit `Boards`: a placement, a removal, an auto-archive) sends the unstored **`card.placement.changed {cardId}`** (nothing else: no column names) to the card's OTHER rooms (the board page refetches on it). Deleting boards re-homes instead of destroying (see Deletions below): each card kept by `boards.BeforeBoardsDelete` gets ONE stored `card.updated` `changed:["placements"(,"home")]` after the commit, card-level, so each surviving board hears it once; a card on deleted boards only goes with them (their `board.deleted`/`project.deleted` covers it).
  - **Notifications** (`planNotifications`, still the only planner, at most one per user per event): one query loads the card and ALL placements with their columns; the event's board must hold a placement (replaces the old `board_id` guard). Watchers come from ONE UNION (`IN` lists over the in-scope columns and boards; constant query count, tested with three placements) and access from ONE `authz.CardViewers` call. A column or board watch counts only when its watcher can view that board; for a placement event every recipient must view the event's board. For `card.archive` the other boards' watched columns include the column each placement left (its `prev_list_id`, in the same query), so a watcher of B's column hears the card leave it. Each notification names one board (`notifications.board_id`): the watched board for a column/board watch, else (card watch, mention, member added) the event's board for a placement event, else the home when viewable, else the first viewable placement. `fromList`/`toList` of a move go only into notifications that NAME the event's board (a notification naming board B never carries A's column names, even for someone who sees both: it travels under B's name to B's project webhooks and channels; a watcher of a card-level archive told under B reads "moved X on B"). `createNotifications` loads the board names in one query; board notification services hear a comment once per placement board on that board's own channel; `notificationCreate` webhooks are scoped to the notification's board.
  - **Webhooks** (`dispatchWebhooks`): once per webhook per logical event. A board webhook matches when its board is in scope (board event types only) and receives that board's copy; a project webhook matches any in-scope board of its project and receives the home's copy when the home is in the project, else the first such board's; an unscoped webhook receives the home's copy (else the origin's).
  - **Activity**: `activity.card` (optional `boardId` context; `card.get?full` passes its context) lists only rows recorded on boards the caller can view (any board the card's rows are on, `BoardLevels`; so a board the card has left keeps its history for that board's viewers), then one row per `COALESCE(origin_id, id)` (the context board's copy, else the oldest viewable one); the dashboard feed filters by access first and then dedupes by origin; `activity.board` is unchanged (card-level events already have a row on every placement board). Rows written before 0801 have no `origin_id` (each is its own event).
  - **Privacy tests** (`notify/fanout_test.go`): per-board rows and publishes with one origin, two envelopes in `events.Query`, notifications per watcher with the right board, webhooks once with their own board's view, archive/close/delete (one row per board, origin-linked, one publish per room, one notification per watcher, B's copy naming B's archive), an archive whose context placement was already archived, the board-only auto-archive, `card.place`/`card.unplace`, home board deletion (re-home, no `card.deleted`), the planner's constant query count with three placements, and a table of every card event type on each side checking that nothing destined for the other board (its actions rows and envelopes, its room, its viewers' notifications, its board and project webhooks, `activity.card`) names the acting board, its columns, labels, fields or project.
- **Write ops (phase 4, `cards/placement_ops.go`)**:
  - `card.place` (`POST /cards/{id}/placements` `{listId, boardId?, position|afterId|beforeId}`): Edit on the card (any viewable placement, worker rule included: `authz.CardEditAccess`) AND Edit on the target board, then: Invalid for drafts, card templates, a target or current board that is a board template, a target column that is not active or closing; Conflict when the card is already on that board (checked again in the transaction; the PK makes a race a Conflict too). Any project. The placement is written with `placed_by`/`placed_at`, then `boards.Landed` (a closing column closes the card, an ordinary one re-opens it; the column's archive-after rule trims that board's placements). Returns the card as `card.get` on the new board. Event `cardPlace` / `card.placed` on the new board.
  - `card.unplace` = **"Remove from board"** (`DELETE /cards/{id}/placements/{boardId}`): `RequireCardOn(Edit)` on that board; Invalid on the card's last placement ("archive or delete the card instead"). `removePlacementsTx` (also `boards.RemoveFromBoards`): a home that leaves first hands over to the **oldest other placement** (`placed_at`, then board id; `is_home` cleared then set, so `cp_home_rehome` moves the `cards` mirror), the placement is deleted, then `pruneAfterLeaving` drops the labels (`labelAllowed`) and members (direct or group membership) that no remaining board allows, exactly the cross-board `card.move` rule generalised to "any remaining board". Returns `{cardId, boardId, newHomeBoardId?}` (the new home only when the caller can see it). Events: `cardUnplace` / `card.unplaced` on that board, and `card.updated` `changed:["home"]` on the new home.
  - `card.placements` (`GET /cards/{id}/placements`): the viewable placements with board, project and column names, column type, position, `isHome`, `placedAt` and `canEdit`; hidden ones are never listed. Its UI route renders the open card sheet's board parts for the live refresh (`cards_boards_live`, see the write half).
- **Which placement a write acts on**: `card.move` (and the claim/release/`card.next` moves) moves ONE placement, picked by `resolveMove`: `boardId` when given (a viewable placement, else not_found), else the placement on `listId`'s board (a reorder or column change there), else the only placement the caller can see (a relocation to `listId`'s board), else Invalid ("on several boards: pass boardId"). The caller must be able to edit that placement (`CardAccess.EditableOn`: Edit there, or the worker rule); a relocation needs Edit on the destination and is a Conflict when the card is already there; the home stays the home. `card.label.add|remove` take `boardId` (required when the caller sees several placements; a label of another board is not_found). `card.duplicate` copies onto ONE board, the context (`boardId` hint, else the home when visible). `card.member.add` accepts a member of any viewable placement board.
- **Card-level actions** (no `boardId`; Edit on any viewable placement): `card.archive` (and `trash=true`) moves EVERY placement, hidden ones included, to its board's archive (trash) list, remembering its column (the context board must have the list, as before; another board gets it created); `card.restore` brings every archived/trashed placement back to its previous column when that is still an open or closing column of its board, else that board's first open column (closing columns land last, so one closes the card); `card.delete` needs every placement in a trash list ("in the trash"); `card.close` sets the per-card flag and moves the context placement as before (into its board's closing column, or out of it when re-opening). One event on the context board, card-level (`card.archive`/`card.restore` mark it `events.CardLevel`; the fan-out writes one row per board, each copy naming only that board's own columns). Claims stay card-level (the lease on `cards`); `card.next` picks from the column's placements (with `moveTo` on another board: that board's placement moves when the card is on it, else the placement of the column it was picked from relocates there, so a card on several boards is never released again as `move_failed`), so two listeners on columns of two boards holding the card hand it out once (`TestCardNextTwoBoardsOneWinner`). ## Closed cards (`cards.is_closed`)
- **The column setting "Close cards that land here"** is `lists.type`: `closed` = on, `active` = off (no second mechanism, no new column).
  The UI never says "type": the column sheet's Properties row **Auto-close** (On/Off popover headed "Close cards that land here" with the help text "Cards moved or added to
  this column are marked closed (with a check mark); moving them to another column re-opens them."), the same `menuitemcheckbox` in the
  column `...` menu, a success-coloured check mark in the kanban column header (`.boards-col-closes`, `role="img"`, aria-label/title "Closes
  cards that land here"; partial `closed_mark_ico`), a "Closes cards" badge in the sheet header, and the mark plus a "Columns that close
  cards" note in the template gallery preview. `archive`/`trash` are system lists and untouched. `card.close` moves a card into the board's
  first closing column (else closes it in place); `board.tree` hides closing columns unless `includeClosed`; `card.next` picks open cards only.
- **Exception: applying a template** (`boards.LandedKeepClosed`): the bulk move of a whole board into the template's first column keeps closed cards closed (with the mark) even though that column is an ordinary one, and skips the archive-after pass; a closing column still closes. Nothing else uses it.
- **One rule, one helper.** `boards.ClosedAfterLanding(listType, wasClosed)`: landing in a `closed` column closes the card, landing in an
  `active` column re-opens it (as before: moving between columns re-opens a card closed in place), landing in `archive`/`trash` **keeps** the
  current value (archiving or trashing a closed card no longer clears it), and a restore is a landing in its destination. `card.close` without a
  closed column closes the card in place; a reorder inside a column is not a landing and keeps it.
- **`boards.Landed(ctx, tx, ...Landing{CardID, ListID})`** (`boards/landing.go`) applies the rule inside the writing transaction, after the rows
  carry their new `list_id`. It takes (card, column) pairs so it can move to per-board placements unchanged, skips drafts and card templates,
  never writes for archive/trash, writes only rows whose value differs (one `UPDATE ... RETURNING` per 500 ids) and returns `LandResult{Closed,
  Reopened}` for events after the commit. Every path that puts a card into a column calls it: `card.create`, `doMove` (card.move, drop,
  archive/restore/close, claim/release with a list, `card.next` with `moveTo`) on a column change only, `cloneCard` (duplicate, from-template,
  recurrence), `card.draft.publish` (after `is_draft=0`), `boards.moveAll` (`list.moveCards`, archiving or deleting a column), `writeImport`
  (import, `board.instantiate`) and `list.update` when the setting changes (below). Writers never compute `is_closed` themselves; a
  table-driven test (`cards/closing_paths_test.go`) lands a card through each path into a column switched on with `list.update`.
- **Switching the setting on a column that holds cards** (`list.update type`, optional `existingCards`, backward compatible): `flip` (the
  default, also when omitted) re-lands the column's cards in the same transaction (`relandList`: on closes the open ones, off re-opens the
  closed ones); `keep` changes only the setting, so the rule applies to cards that land from now on and the cards already there keep their
  state. Any other value is a validation error; without a type change `existingCards` is ignored. Events: `list.updated` with `type`,
  `closes`, `existingCards`, `closed`/`reopened` counts (the column Activity reads "set this column to close cards that land here and closed
  the 12 cards in it" / "stopped closing cards ..."), plus one `card.updated` per flipped card with `changed: ["isClosed"]`, `isClosed`,
  `auto: "listType"` and `quiet: true` (see Quiet events). The read-only op **`list.typePreview`** (`GET /lists/{id}/type-preview[?type=]`,
  Edit level, `type` defaults to the opposite of the current one) returns `{cards, willClose, willReopen}`; its UI route renders the confirm
  (`boards_list_closes_confirm`, into `#ls-closes-confirm` in the sheet or `#lcc-{id}` in the menu): with nothing to flip a form that applies
  on load, else "Close 12 cards now?" / "Re-open 12 cards?" with the default "Close 12 cards" (focused), "Leave them open" / "Keep them
  closed" (`existingCards=keep`) and Cancel. Only the final PATCH forms carry `data-ls-form="type"`; the menu re-places itself after the swap.
- **Invariant** (a rule applied when a card lands, not a constraint on rows): a non-draft, non-template card that lands in a closing column is
  closed. Migration `0403` backfilled it once (no events, `updated_at` untouched); cards that lost the flag when archived before this rule cannot
  be recovered. With `existingCards=keep` an open card can sit in a closing column (or a closed one in an active column) until it moves; such a
  card is offered by `card.next` like any open card, moving it out still notifies `reopenCard` (the planner reads the list types), later edits of
  the column (name, colour, WIP, description) never re-land it, and an export/import or template round trip brings it back closed (import
  lands closing columns).
- **Export/import**: `exportCard.isClosed` (omitempty). Import stores the file's value and then lands the cards of closed-type columns, so a file
  can never put an open card in a closed column; files without the field import open outside closed columns. Published templates drop it (like
  due completion: progress does not travel), built-in manifests do not carry it.
- **The mark** (`_closed_mark.html`, `{{template "closed_mark" true}}`): an inline 14px round check (circle plus tick, flat strokes, `--success`)
  before the title, with `title="Closed"` and the screen-reader text "Closed: " (pass `false` where visible text already says Closed). Inline
  SVG because the icon sprite exists only on the board page, and `#i-check` is the checklist glyph. Shown on kanban and grid tiles, list-view
  rows, calendar chips and the unscheduled rail (`card.calendar` returns `isClosed`), the public board, the share page (`card.share.view`
  `isClosed`), and inside the card sheet's success badge "Closed". A closed tile's title is `--fg-2` (no opacity fade, no strike-through), and a
  closed card's due date is shown neutral (never "overdue"/"due soon" on tiles or in the sheet), matching board statistics.
  The mark is rendered server-side only when the card is closed; it follows changes because the tile is redrawn: `x` refreshes the board, a
  drop that crosses a closed/active column boundary refetches the tile (`boards_dnd.js`, keeping keyboard focus), a switch of the closing setting in the
  column sheet refreshes the board behind it, closing the sheet refetches the tile (board) or the
  month grid (calendar; the sheet's close listener is a capture listener on `document` because the calendar loads `cards_ui.js` before the
  layout's `<dialog id=modal>`), and other tabs follow the SSE refresh.

## Archive after N (`lists.archive_after`, migration 0310)
- **The setting**: a column with `archive_after = N` (1..10000, `boards.MaxArchiveAfter`; NULL = off, `0` clears it) keeps at most N cards.
  Whenever a landing takes it over N, the cards that have been in the column longest go to the board's archive list. It is independent of the
  soft WIP limit (both can be set; nothing ties them). Archive/trash lists cannot carry it (`list.update` on them is forbidden). It is allowed
  on closing columns (the expected use: "Done, keep the last 30"; archived cards keep their closed mark).
- **The rule** (`boards/archiveafter.go`, `planArchive`, the single source for the landing step, `list.update`'s confirm count and
  `list.archivePreview`): counted = every card in the column except drafts and card templates (closed cards count); oldest first = smallest
  `list_changed_at`, ties by `position` (top of the column first) then id (timestamps have one-second precision; bulk moves stamp one time on a
  batch); the cards that just landed go last and the newest `min(N, landed)` of them are never archived (a single card that lands is never the
  one that goes; a batch larger than N, e.g. `list.moveCards` of 50 into N=30, keeps its newest 30); cards with a **live claim**
  (`claimed_by` and `claimed_until >= now`, the inverse of `card.next`'s pick) are skipped, so the column may sit above N until the claim ends;
  **cards with a recurrence rule** (`cards.recurrence` non-empty) are skipped the same way, **for now** (maintainer decision: archiving one
  would stop its occurrences). Skipped cards still count toward the column's total; a card both claimed and recurring is counted once, as
  claimed; both counts are clamped to the cards that really stay over N.
- **Where it runs**: step 2 of `boards.Landed`, inside the landing's own `BEGIN IMMEDIATE` transaction, so the count is exact and concurrent
  landings serialise (test: 20 concurrent creates end at N). Every landing path therefore enforces it (create, move incl. cross-board and
  drop, claim/release with a list, `card.next moveTo`, draft publish, duplicate, from-template, recurrence spawn, `list.moveCards`, restore).
  **Restoring an archived card into a full column archives that column's oldest other card** (the restored card just landed). A type switch
  (`relandList`) does not trim. When a claim ends, `card.release` (without a move) and the lease sweeper (`cards.SweepClaims`) call
  `boards.EnforceArchiveAfter` for the card's column, which may archive the released card itself if it is the oldest. Moving a card out lowers
  the count; nothing is ever un-archived. Imports and `board.instantiate` trim each capped column after the inserts (top of the column first,
  no per-card events: the board is new). **Recurring cards (decision, for now)**: the rule skips them (above), so it never stops a series.
  The occurrence spawn (`RunRecurrence`) clears the old card's rule in the same transaction that lands the new one, so that landing (or
  the next one) may archive the old card; clearing a rule by hand archives nothing until the next landing or a re-sent `archiveAfter`
  (no new enforcement path). A card archived by hand still stops spawning until restored (`RunRecurrence` only reads active/closed
  columns). Test: `TestArchiveAfterSkipsRecurringCards`.
- **How a card is archived** (`applyArchive`): exactly as `card.archive` moves it: into `SystemList(board, "archive")` (created on demand), appended
  oldest first, `prev_list_id` = the column (so `card.restore` brings it back), `list_changed_at`/`updated_at` = now, `is_closed` kept. One
  `UPDATE ... CASE id` per 500 cards; the whole pass is one transaction (5000 -> 30 took ~1.9 s in a test including the 4970 events).
- **Setting it on a column that holds cards (retroactive)**: `list.update archiveAfter=N` applies at once whenever the request names
  `archiveAfter` (setting, lowering, or re-sending it after a claim ended; other edits such as a rename never archive). If that would archive
  K > 0 cards and `confirmArchive` is not true, the op returns **409 conflict** "archiveAfter=30 would archive 64 cards now (the column holds 94);
  resend with confirmArchive=true", counted inside the write transaction, and changes nothing. Raising N or turning it off archives nothing.
  Applying the same N twice is a no-op. The read-only **`list.archivePreview`** (`GET /lists/{id}/archive-preview?archiveAfter=N`, Edit level,
  N defaults to the current setting) returns `{current, keep, cards, willArchive, skippedClaimed, skippedRecurring}`; its UI route renders the confirm
  (`boards_list_archive_confirm`, into `#ls-archive-confirm` in the sheet or `#lac-{id}` in the menu): with nothing to archive a form that applies
  on load, else "Archive 64 cards now?" with the column/keep wording, the default "Archive 64 cards" (focused, posts `confirmArchive=true`) and
  Cancel.
- **Events** (after commit, `boards.EmitAutoArchived(e, LandResult)`, called by every landing path): one `cardMove` per archived card with stream
  type `card.archived` and data `{fromListId, toListId, auto: "archiveAfter", keep: N, quiet: true}` (agents, webhooks and the durable stream see
  every card leave; watchers get nothing: Quiet events), then one `list.updated` summary `{id, autoArchived: K, keep: N}`. The column Activity
  shows the summary ("auto-archived 64 cards: the column keeps the newest 30"; `events.Recent` leaves quiet per-card events out of the column
  feed) and setting changes ("set auto-archive: keep the newest 30 cards" / "turned auto-archive off"); the card's own activity reads
  "auto-archived the card: its column keeps the newest 30 cards". The board page toasts the summary once (`boards_board.js`, SSE
  `list.updated` with `autoArchived`) and redraws through its usual debounced refresh.
- **UI**: column sheet Properties row **Auto-archive** (popover "Keep the newest N cards", a number and Set, "Turn off" when on, the confirm
  slot), a "Keeps newest N" chip in the sheet header, an **Auto-archive** row in the column `...` menu (number + Set, "Turn auto-archive off"),
  and a small archive-box-with-clock glyph in the kanban column header (`.boards-col-archive`, `role="img"`, label "Auto-archive: keeps the
  newest N cards"; partial `archive_after_ico` in `_archive_after.html`) and in the template gallery preview.
- **Travels** wherever the WIP limit travels: `List.archiveAfter` (list.get/list/create/update, `board.get`, `board.tree`, MCP board resource),
  export/import (`exportList.archiveAfter`, out-of-range values dropped), published templates (`TemplateColumn.archiveAfter`), built-in
  manifests may set it (none do), the gallery preview.

## Archive view
- **UI and URL state**: the board filter row's **Show** control chooses **Active** (the default), **Archived** or **Trash**.
  `?show=archived|trash` is shareable, reload-safe URL state and bypasses the board's default-view redirect, including on
  Calendar/Map-default boards. Either choice replaces `#board-body` with the Archive table; returning to Active restores
  the board's normal view. Viewers can browse the table; mutations require Edit.
- **Table**: Label and Member are single-select controls that map directly to the op's singular `labelId`/`memberId`
  filters; Member offers Any member, Me, Unassigned or one concrete member. Text uses `q`; **From** (`fromListId`) and
  **Since / Until** (`since`/`until`) are additional facets. Sort is archived date (newest first by default), name or From.
  It shows 50 rows per cursor page and **Load more** appends the next page. Month heading rows appear only for
  archived-date sorting and use local time. Rows show the card name (opening its sheet), From column (`(removed)` when the
  previous column is gone), archived date (relative text with an absolute title), labels, members, a closed mark, and
  "also active on <board>" only for other viewable boards where the card still has an active/closing placement. Hidden
  boards are never named or counted. The header carries the filtered total; empty states distinguish an empty
  archive/trash from filters with no matches.
- **Row and bulk actions**: editors get **Restore** on each row and **Delete forever** in Trash where the row's
  `canDelete` is true (every placement of the card is in trash). Checkboxes and the bulk toolbar restore or delete the
  selected rows; **Select all N matching** applies to the whole current filter, not only loaded rows, and asks for
  confirmation with the exact count before submitting `all=true` and `confirmCount`. A changed count is a 409, so a stale
  selection cannot silently act on a different set. A local card-sheet restore/delete refreshes an idle Archive table;
  SSE and other-tab changes do not auto-refresh it, protecting selection and typed filters. Viewers have no selection or
  mutation controls. The phone layout keeps filters and row actions usable; all behavior stays in server-rendered HTMX
  and static delegated JavaScript under the normal CSP (no inline scripts or handlers).
- **List contract**: `GET /boards/{boardId}/archive` needs View on the board. It lists that board's `archive` placements
  (`kind=archived`, the default) or `trash` placements, excluding drafts and card templates. Filters are `q`, `labelId`,
  `memberId`, `fromListId`, `since` and `until`; `q` is escaped substring matching on name or description, and `labelId`
  matches only labels visible on the acting board. Dates accept RFC3339 or `YYYY-MM-DD`, normalized to UTC: `since` is
  inclusive, RFC3339 `until` is inclusive, and a date-only `until` includes the whole day. Sort is `archived|name|from`
  (`archived desc` by default), with `dir=asc|desc`; limit defaults to 50 and is capped at 200. Rows carry the card id/name,
  `archivedAt` (the placement's `list_changed_at`), previous-column id/name, card-level `closed`, board-visible labels,
  members, `alsoActiveOn`, `canRestore` and `canDelete`. `canRestore` reflects Edit on this board. `canDelete` is true only
  for a Trash row with Edit and every placement in trash; hidden placements take part in that safety check but their
  boards are never returned. `alsoActiveOn` names only other viewable boards with an active/closing placement; hidden
  boards are never named.
- **Paging and performance**: filtering, sorting and counting run in SQL over the board's placements. `cp_board(board_id)`
  keeps the starting set board-local and `lists_board(board_id, position)` resolves that board's system lists; normal tile
  and board-tree queries are unchanged. `total` counts the whole current filter. The opaque `nextCursor` is bound to the
  board, filters and sort and carries a keyset position with a stable card-id tie-breaker, not an OFFSET; an empty cursor
  ends the pages. Row decorations are batched rather than fetched per card. The 10,000-archived-card benchmark is the
  scale guard for a page.
- **Bulk contract**: both writes need Edit on the board and accept either `cardIds` (maximum 500) or `all=true` plus the
  archive filters and `confirmCount`. Both the API and UI POST bulk restore/delete routes use the server's heavy rate-limit
  class: `all=true` is unbounded and fans out per-card events/webhooks. For `all`, `confirmCount` is required (missing is a 400
  validation error) and must equal the current matching total or the op returns 409. With `all=true`, `card.restore.bulk` also accepts `kind=archived|trash`; the
  matching set and `confirmCount` are then scoped to that kind. Omitting `kind` keeps the backward-compatible
  restore-both behavior. Transactions are chunked in batches of 500, so earlier chunks stay committed if a later one fails, and `Delete forever` availability and the `skipped` count consider every placement of a card, including placements on boards the viewer cannot see (only a boolean is reported, never a name). `card.restore.bulk` uses exactly `card.restore`
  semantics for every selected card: every archived/trashed placement returns to its previous column only when it is still
  an active or closed column on that same board (a valid previous closed column closes the card), otherwise that board's
  first `active` column by position; if no active fallback exists, restore fails. Closing plus archive-after rules apply.
  `card.delete.bulk` is trash-only and skips cards that are not in trash on every placement. Results are
  `{restored, skipped}` / `{deleted, skipped}`.
- **Events and privacy**: each changed card emits its normal card-level restore/delete event with `quiet:true` and
  `auto:"bulkRestore"` or `"bulkDelete"`. These events are still durable and reach SSE/webhooks, but notify no watchers;
  the initiating board gets one activity summary. Card-level effects still include hidden placements, while response
  fields, activity and event copies never name a board the caller cannot view.

## Colours: board, columns, cards
- Storage: `boards.color` and `lists.color` hold a lowercase `#rrggbb` (migration 0301). Presets (crimson, orange, amber, lime, green, teal, sky, blue, indigo, violet, pink, slate) and legacy Planka names are accepted by the ops and resolved to hex on write; `""` clears. Labels keep a name or hex. Everything is validated server-side against `^#[0-9a-fA-F]{6}$` / known names (`boards.NormalizeColor`); templates only ever emit a validated hex (`boardsListAttr`, `boardsBoardAttr`, `boardsTileFill`), never the stored string.
- Board colour tints the board canvas (`--tint-board`, 8% light / 6% dark over `--bg`) and draws a 4px full-colour bar under the board header; the project page shows it as a flat stripe on the board tile.
- **Board statistics** (project page tiles, op `board.stats`): `boards.Stats(e, ids)` (boards domain, read-only over cards/lists/actions/memberships plus the in-memory listener registry) filters ids through `authz.BoardLevels` (the bulk form of `BoardLevel`, same rules) and costs a constant number of queries for any number of boards (a test counts them through a wrapping driver). `boards.ActivityLess` is the one ordering rule (newest `actions.created_at` first, then position, then id) shared by the page and the op. The projects domain calls `Stats` once per page load and builds the tile view model (`projects/tiles.go`: the 4-row budget, sparkline, sentence); it never reads cards or lists itself. Tiles are not live and never re-sorted on the client.
- Column colour: always a 3px full-colour top bar. In `pill` mode the body also gets a faint tint (`--tint-list`, 6% over `--list-bg`); in `fill` mode **columns stay neutral** (`--list-bg`, top bar only) so a filled card never sits on a second colour. Uncoloured columns are unchanged.
- Card colouring is a per-board setting `cardColorMode`: `pill` (default, label pills) or `fill`.
  **Precedence: the first label (by label order: `labels.position`, then id) decides the card colour; colours are never mixed.** In `fill` mode the tile is a tint of that one colour (`--tint-fill` over `--tile-bg`) with a 3px full-colour left edge, text stays `--fg`, the colouring (first) label gets no chip (the fill is its indicator; its name stays in the card for screen readers), the other labels become natural-width neutral outline text chips (`.boards-lchip`, wrap onto more lines, ellipsis only for a single name wider than the tile), and badges/avatars/progress use neutral surfaces. Cards without labels look normal. Label order is user-controlled (Board Settings, Labels: drag or arrows).
- `scripts/check-contrast.py` checks `--fg`/`--fg-2`/`--muted` on every preset and Planka colour on the board canvas tint, `--fg`/`--fg-2` on pill-mode column tints and filled tiles, in both themes, the closed mark (`--success`, 3:1 non-text) on every filled tile and on the surfaces it sits on, caps the tints (board <=10% light / <=8% dark, column <=8%) and requires the `prefers-color-scheme` tint block to equal the `[data-theme=dark]` one.
- Popovers (list menu, card quick edit, filter dropdowns) are `position:fixed`; while open the list menu is **portaled** to `#popover-root` (a child of `<body>`) so no column, scroller or tile can paint over it. `window.WeavePop.open` (list id -> menu) keeps the live refresh from touching a column whose menu is open and sweeps menus whose column disappeared.

## Watching and notifications
- **Scopes** (all explicit opt-in): board (`board_subscriptions`, ops `board.subscribe|unsubscribe`, boards domain), column (`list_subscriptions`,
  migration 0308, `list.subscribe|unsubscribe`, boards), card (`card_subscriptions`, `card.subscribe|unsubscribe`, cards). Anyone who can view the
  board may watch. Toggles never call `ops.Emit` (an activity row would publish who watches what) and do not live-update other tabs.
- **Card rows**: `card.subscribe` = explicit watch (`is_permanent=1`, clears `muted`); `card.unsubscribe` = **mute** (`muted=1`, migration 0402,
  row kept or created). Muted rows never notify, even through a watched column or board, are never re-added by auto-watch, and are listed
  separately. Auto-watch (`INSERT OR IGNORE`, `is_permanent=0`): creating a card (pref `subscribe_own_cards`, on by default since migration 0102;
  card.create, duplicate, from-template, inbox draft), commenting (`subscribe_to_card_when_commenting`, via `cards.AutoWatchComment`) and being
  added as a member. Agents (`users.is_agent`) never auto-watch. `is_permanent` only reports "watched on purpose".
- **What notifies** (`notify.planNotifications`, the only place): `cardCreate` (not drafts) -> `createCard`; `cardMove` between columns ->
  `moveCard`, into/out of a closed-type column -> `closeCard`/`reopenCard` (one event, one type); `cardUpdate` carries `Data.changed` (field
  names set by the cards domain): `isClosed` -> close/reopen, `dueDate` (set or changed, not cleared) -> `setCardDueDate`; `commentCreate` ->
  `mentionInComment` (mentioned viewers) / `commentCard`; `cardMembershipCreate` -> `addMemberToCard` (the member only). Edits, labels, tasks,
  attachments, position changes are silent. Column watchers match the card's current column, and for a move both source and destination.
- **Quiet events**: an event with `Data["quiet"] == true` (`notify.Quiet`) never notifies anyone: `planNotifications` returns nil before any
  rule (watch, mention, member). The actions row (activity), SSE, the durable event stream and webhooks are unchanged, so agents and
  integrations still see every change. Bulk side effects use it so a watcher does not get one notification per card: the closing switch's
  per-card `card.updated` (`auto: "listType"`). Ordinary single-card moves are never quiet (moving one card into a closing column still sends
  one `closeCard` per watcher). Auto-archive (`auto: "archiveAfter"`, see Archive after N) is quiet too: its per-card `card.archived` events never
  notify, while the card whose landing triggered it notifies as usual. Applying a template (`auto: "applyTemplate"`) marks its per-card moves the same way.
  Archive-view bulk restore/delete (`auto: "bulkRestore"` / `"bulkDelete"`) mark every per-card event quiet too, then write one board activity summary.
- **De-duplication**: per event ONE query collects card, column(s) and board watchers; at most one notification per (user, event), reason in
  `data.via` (`card` > `list` > `board`; `data.viaList` names the column, the destination when both are watched). The actor is skipped, a mention
  beats a watch, a muted card silences every watch (not a direct mention or being added), drafts/templates never notify, and one
  `authz.CardViewers` call (per placement; see "Placements", notifications, for cards on several boards; formerly `authz.ViewersAmong`) (same rules as `BoardLevel`, plus deleted/deactivated) drops people who cannot view the event's board (for a
  cross-board move: the destination). The planner's query count is constant in the number of watchers (test). Delivery (SSE, services, e-mail,
  `notificationCreate` webhooks) runs once per created notification, so the plan's de-duplication covers every channel.
- **Per-viewer flags never travel**: `card.get isSubscribed` is cleared on the card emitted in event payloads (`cards.emitKind`); `board.get
  isSubscribed` lives on `BoardDetail` (not `Board`), `list.get isSubscribed` is set by that handler only, card watch state (`via`, `muted`) is on
  `card.options`. Public and share views carry none of them.
- **Read side**: `subscription.list` (notify, View-filtered with `authz.BoardLevels`) feeds Settings > Watching (`notify_watching.html`, lazily
  loaded into `auth_settings.html`). Messages (`notify.Message`) end with the reason ("You get this because you watch the column Review.");
  the in-app list shows it as `reason`. No rate limit or digest in v1.

## Security model
Controls every contributor must preserve (tests: `internal/server/*_test.go`, `internal/cli/safety_test.go`, `internal/domain/auth/*_test.go`):
- **Authentication**: OIDC only (state cookie + nonce + PKCE S256; `email_verified` false/"false" denies; userinfo claims are merged only when its `sub` equals the ID token `sub`). Sessions are browser-only; the CLI/agents use API keys (`Authorization: Bearer` or `X-API-Key`). Cookies are `HttpOnly`, `SameSite=Lax` and `Secure` whenever `WEAVE_BASE_URL` is https (never inferred from `X-Forwarded-Proto`). `safeNext` only returns same-site absolute paths.
- **Identity binding**: `users.oidc_sub` holds `issuer|sub`. `OIDCLogin` looks the subject up first; otherwise it links by e-mail only to an account whose `oidc_sub IS NULL`, via one `UPDATE ... WHERE oidc_sub IS NULL` checked with `RowsAffected` (a lost race is a denial). An e-mail match on an account bound to another subject is a 403 plus an `AUDIT` log line. `user.relink` (admin; clears `oidc_sub`, ends sessions, emits `user.relinked`) and the host-only `weave admin relink --email` are the only ways to rebind.
- **Sessions and keys**: sessions default to 24 h (`session.hours` admin config, `WEAVE_SESSION_HOURS` pins it; expiry redirects to `/login` and on to the OIDC provider, which owns the real lifetime); `session.maxIdleMinutes` (`WEAVE_SESSION_MAX_IDLE_MINUTES`, admin config) bounds idleness for everyone, combined with the stricter per-user auto-logout. API keys live in the `api_keys` table (migration 0901; the old `users.api_key_*` columns are dead, a scan test enforces it): a person holds any number (one per computer; `WEAVE_MAX_API_KEYS`, default 50, 0 = unlimited), each with a name, `expires_at` (`expiresInDays` on `apikey.generate`, `agent.create`, `agent.rotateKey`; default never) and `last_used_at` (written by authentication at most once per 10 minutes per key, never for background polling, a failed write never fails the request). `apikey.generate` ADDS a key and never invalidates another; `apikey.revoke` needs `keyId` (scoped to the resolved user) or `all=true`; `apikey.list` shows name/prefix/dates, never the key or hash; list and generate are owner-only. An agent account holds exactly one key (`agent.rotateKey` replaces it; an agent principal cannot call `apikey.generate`). `weave admin mint-key` ADDS a key named "mint-key". User/agent output derives `hasApiKey`/`apiKeyCount`/`apiKeyPrefix`/`apikeyExpiresAt`/`apikeyExpired` from the keys (newest). Security note: a key can create more keys for its owner, so revoking a leaked key does not stop a sibling it minted; every key is listed with its last use so strays are visible. An expired key yields 401 with an explanatory message (`ops.Env.AuthMsg`). `user.sessions.revokeAll` signs a user out everywhere.
- **Webhook scopes** (`internal/authz/webhooks.go`, migration 0610): global and project-scoped webhooks are admin-only (instance
  integrations; the console's scope picker names only projects the admin can see and boards the admin manages); board-scoped ones are
  created, seen and managed by anyone with Manage on the board, administrators included only through a real membership
  (`RequireWebhookScope`, `RequireWebhook`: missing access is not_found). Every manager of a board sees every webhook of that board,
  whoever created it, so nothing keeps delivering a board's events out of its managers' sight. A webhook created by a non-admin is
  flagged `strict_dest=1` (`userCreated`) once and never relaxed (a non-admin's edit sets it, also on a board webhook an admin created). Non-admins cannot set
  `projectId`/`userId`, drop the board scope or move it to a board they do not manage. A board webhook may subscribe to, and receives,
  only `BoardWebhookEvents` (card/list/label/comment/task/attachment/custom-field/membership/board update events) of its own board:
  `dispatchWebhooks` requires both the resolved board and the event type, so `notificationCreate` (one user's), user, project, config,
  notification-service and webhook events never reach it. Board webhook changes go to the board room (realtime only), global/project ones
  to `global`, always without URL, token or secret. Deliveries (`webhook.deliveries|test|retry`) are visible to whoever manages the
  webhook; non-admins get response bodies capped at 512 bytes (256 from `webhook.test`), admins the stored 2 KiB. Caps: name 255, URL 2048,
  token/secret 1024 printable characters, `WEAVE_WEBHOOKS_PER_BOARD` (default 20, 0 = off). Webhook tests and redeliveries are in the
  heavy rate-limit class. Delivery errors no longer embed the request URL.
- **Webhook destinations (SSRF)**: admin-created webhooks keep the admin policy (`HTTPClient`, no restriction). Strict webhooks are sent with
  `strictClient` (`notify/webhook_ssrf.go`): no proxy, a `DialContext` that resolves the host itself (`LookupIP` seam), refuses the whole
  answer if any address is blocked and dials the checked IP literal (so DNS rebinding cannot reach a blocked address), at most 3 redirects
  (http/https only; each hop goes through the same dialer). Always refused: loopback, unspecified, link-local incl. 169.254.169.254 and
  fd00:ec2::254, multicast, broadcast, 0.0.0.0/8, metadata host names, `localhost`/`*.localhost`, IPv4 embedded in NAT64/6to4 addresses that
  would be refused; refused by default: RFC 1918, ULA fc00::/7, CGNAT. Admin switch `webhook.userAllowPrivate` (env
  `WEAVE_WEBHOOK_USER_ALLOW_PRIVATE`, Admin console > Settings > Webhooks) allows private networks for homelab receivers;
  `WEAVE_NOTIFY_ALLOW_HOSTS` overrides every block for the hosts/IPs/CIDRs it lists. The same check runs when the URL is saved (fails closed
  if the name does not resolve). Strict delivery failures are stored as the generic `could not deliver: destination unreachable or not
  allowed` (detail in the server log, without the URL).
- **Webhook signatures**: every signed delivery carries the legacy `X-Weave-Signature` and `X-Weave-Signature-V2: t=<ts>,v1=<HMAC(secret, ts "." body)>` sharing one timestamp, so receivers can enforce a replay window (`docs/WEBHOOKS.md`).
- **Transport**: `Strict-Transport-Security: max-age=15552000` only when `WEAVE_BASE_URL` is https (`internal/server/hsts.go`; `WEAVE_HSTS=off`, `WEAVE_HSTS_MAX_AGE`).
- **Supply chain**: release `SHA256SUMS.txt` is signed with ed25519 (`internal/relsign`, CI secret `RELEASE_SIGNING_KEY`; `weave verify-release`; installers verify, `install.sh` only over https). Dockerfile, CI and runner images are pinned by digest (`scripts/update-pins.sh`, `docs/MAINTENANCE.md`).
- **Admin = system administration, no content access**: the `admin` role runs the instance (users, groups, SSO, settings, branding,
  backup, storage, reindex, agent prompt defaults and hidden built-in templates, global/project webhooks, agent ACCOUNT control, the
  ownerless-project recovery) and carries **no** access to any project, board, card, comment, attachment, search result, dashboard,
  export, SSE room, notification, watch list, template or board webhook. `BoardLevel`/`BoardLevels`/`ProjectLevel`/`ProjectLevels`/
  `IsBoardMember`/`ViewersAmong`/`TemplateVisible` know nothing about roles: an admin sees exactly what they own or are a member of,
  like everyone, and gets **not_found** for everything else (never forbidden). Projects and boards belong to their owners and they
  manage them. The only ways an admin reaches someone else's content are the audited recovery path (naming themself manager of an
  ownerless project) and the residuals below; there is no impersonation (yet). `authz.SystemAdmin` is the one predicate for system
  powers; `TestNoAdminContentBypass` (`internal/authz/nobypass_test.go`) parses the code and fails on any new admin-role decision
  outside its allowlist of system sites (and on any in a content function or a template), `internal/server/admin_persona_test.go`
  requires the admin without membership to get the outsider's answer from every non-system op and route (with stale watches,
  card memberships, favourites and old notifications seeded), and the capability matrix asserts the admin row holds no content control.
  Old notifications only show boards the reader can still view. Hosts that mint a break-glass admin key (`weave admin mint-key --role
  admin`) get an account with system powers and no content. **Residuals** (system features the maintainer kept; an admin can use them
  to reach content, so they are trust boundaries, not bypasses): global and project webhook payloads and their delivery logs, the
  database backup download, rotating an agent's key (then acting as that agent on its boards), adding themself to a user group that
  holds board memberships, `user.relink` (then signing in as that person through the IdP) and naming themself manager of an ownerless
  project. Audit coverage: `agent.rotateKey`, `apikey.revoke` (an admin revoking ANOTHER person's keys; the owner revoking their own writes nothing), `group.member.add` and `user.relink` (plus `weave admin relink`) write an
  `admin_audit` row (below) and an `AUDIT` line; recovery writes `project_recoveries` plus an `AUDIT` line; webhook changes emit
  `webhook.*` events. Not audited: the backup download (access log only), the host-only `weave admin mint-key` (stdout and the host
  shell only) and the IdP team-group sync on sign-in (`weave-team-*`, owned by the IdP, not an admin-side action). `apikey.generate`
  and `apikey.list` are owner-only, so an admin cannot mint or list another person's keys through the API (revoking them is audited).
- **Admin audit log** (`auth/audit.go`, migration 0111 `admin_audit`, op `audit.list`, Admin console > Audit log): **rule: an
  admin-side action that changes access leaves an audit row**, written in the SAME transaction as the change (`writeAudit` on the
  change's `*sql.Tx`), then an `AUDIT` log line after commit. Covered: `apikey.revoke` by an admin on someone else's keys (details: count, key display prefixes, all/one; never a key or hash), `agent.rotateKey` (any rotator: creator, board manager, admin;
  details = the new key's display prefix and expiry only, never the key or its hash), `group.member.add` (every add that inserts a
  membership, also each of `group.create`'s `memberIds`, through the shared `addGroupMember`; `details.self` when the actor adds themself; an `INSERT OR IGNORE` no-op re-add writes nothing), `user.relink`
  and the host-only `weave admin relink` (source `host`, NULL actor; details = sessions ended; the SSO subject is not stored).
  Columns: id, created_at, action, actor id/name/email, target kind/id/name/email (text snapshots, no foreign keys, so rows outlive
  the people), details JSON, source `ui` (a `/ui/` request) | `api` (REST or in-process) | `host`. `audit.list` (`GET /audit`,
  `AuthAdmin` plus `authz.RequireAuditLog`: human admins only, an admin-role agent account is refused) pages newest first with an
  opaque `before` cursor (`created_at|id`), `limit` (50, max 200) and an `action` filter; the page (`/admin/audit`, `adminOnly`)
  lists action, target, actor, source and time and never links into content. Project recoveries are NOT merged in: the projects
  domain imports auth, so a merge would need a hook and a two-table paged merge; they keep their own log on Orphaned projects
  (linked from the audit page).
- **Roles and ownership** (`internal/authz`, package comment): roles are `admin`, `boardUser`, `worker`, `guest` (the IdP's groups decide; the old `projectOwner` role and its group are gone, migration 0103). `CanCreateProject` = a signed-in human (`!Principal.IsAgent`) with role admin or boardUser; the creator becomes the project manager. Project managers (any active person except guests and agents, `projects.CanBeManager`) have Manage on the project and all its boards; the project's creator (`owner_manager_id`) steps down only themself (`CanRemoveOwningManager`); co-managers remove that row only once the owner's account no longer counts (deactivated, deleted, agent, guest); nobody else, administrators included, can push an active owner out of their project, and a project keeps at least one manager. Board memberships carry `role` owner|editor|viewer (+`can_comment`; `authz.MembershipLevel`): **owner** = Manage on that board only (settings, members, sharing, template publishing, delete), never on the project, its other boards, project labels or the board order (`board.move`/`position` need project Manage); owners are user memberships of active non-guest, non-agent people. Any membership on a board gives project View. **Board creation** is one function, `authz.CanCreateBoard` (`RequireCreateBoard`: not_found without project View, else forbidden): project Manage, or with `projects.board_creation='members'` (migration 0202, default `owners`) any project member who passes `CanCreateProject`; it gates `board.create`, `board.instantiate`, `board.import`, the template gallery routes and every Create board button. `insertBoard` makes a creator without project Manage the board's owner (an editor otherwise). Last-owner rule (`boards.checkOwnerLeaves`): an owner membership may be removed or downgraded only if another owner remains or the caller has project Manage, so an owner cannot lock themselves out (project managers can always manage the board anyway). Board memberships never travel in exports or templates, so ownership never leaks into a published template. Pickers for managers and board members list the caller's own directory (`user.list`/`group.list`); `board.member.*` and `project.manager.list` return e-mail addresses only to admins (user directory data, as in `user.list`) and the person themself. Any member may leave a board (Board settings > Members & access > Leave board, `board.member.remove` of their own membership; disabled for a sole owner by the last-owner rule).
- **Admin recovery path (ownerless projects)** (`internal/authz/recovery.go`, `projects/orphans.go`, migration 0203): a project is
  ownerless when none of its `project_managers` rows belongs to an active person (`activeManagerSQL`: not soft-deleted, not deactivated,
  not an agent, not a guest; hard deletes cascade the rows away). `project.orphans|reassign|recovery.list` are `AuthAdmin` plus
  `authz.RequireProjectRecovery` (a human admin, never an agent account) and deliberately do NOT use `ProjectLevel`: the admin role
  has no content access, recovery is the narrow audited exception. The listing carries only id, name, created date, board counts and former managers,
  never board or card names. `project.reassign` re-checks ownerlessness inside its write transaction and refuses a project that still
  has an active manager (that would be an admin takeover), requires an eligible target (`CanBeManager`, active), moves the owning-manager
  mark when its holder is inactive, and writes the audit row in the same transaction: `project_recoveries` (no foreign keys; project,
  target and actor names/e-mails snapshotted; source `admin` or `host`; previous managers as JSON), plus an `AUDIT` log line. After
  commit it emits `project.reassigned` on `global` with ids only and `projectManager.created` to the new manager's user room (there is
  no "added as manager" notification type). Host-only: `weave admin preflight` (read-only, `db.OpenReadOnly`: `mode=ro` + `query_only`,
  no migrations, only columns that exist since 0001/0800, so it runs on a not yet upgraded data directory) and `weave admin adopt`
  (break-glass on any project, audited with source `host`). See `docs/MAINTENANCE.md` "Before upgrading to ownership-based permissions".
  The admin Users page warns before a deactivation or deletion leaves projects without an active manager (`projects.WouldOrphan`,
  counts only, through the `auth.OwnershipImpact` hook) and links to Orphaned projects.
- **Capabilities (what the UI shows)** (`internal/authz/caps.go`): pages never re-derive a permission. They ask `authz.Home(e)`,
  `authz.Project(e, id)`, `authz.Board(e, id)` or `authz.Card(e, id)` for a typed struct (CanManage, CanCreateBoard, CanOpenSettings,
  CanManageMembers, CanShare, CanPublishTemplate, CanManageAgents, CanManageWebhooks, CanEditLabels, CanEdit/CanEditExtras on cards...)
  computed from the same predicates the ops call; rules that used to live in a domain (the worker card-edit rule, project-wide label
  edits, removing the owning manager, the project list's manager flag, the tile quick edit on a worker's own cards) moved into authz (`RequireCardEdit`, `RequireBoardLabels`,
  `CanRemoveOwningManager`, `ProjectLevels`) and both the op and the struct call them. A control or settings section is rendered iff
  its op allows the caller, and hidden controls leave no empty section. System powers (`SystemAdmin`: admin console, global/project
  webhooks, recovery) are separate fields from content access; the admin role has no content access, so the admin persona's row in
  the matrix holds no content control (`TestCapabilityMatrixAdminHasNoContentControls`). Rule: **add a control => give it a
  `data-cap` hook and add a row to the capability matrix** (`internal/server/caps_matrix_test.go`: page x persona x control ==
  capability == op result).
- **Authorization**: every op declares `Auth` and checks board/project access in the handler (`internal/authz`); `internal/server/authz_sweep_test.go` walks every op and web route as anonymous, outsider and read-only callers against an explicit allowlist, and `admin_persona_test.go` does the same for an administrator without memberships (compared to the outsider). Add new public/self ops to that allowlist only with a reason. Idle auto-logout counts only real interactions: polling, SSE re-auth and `/ui/presence` (see `isBackground`) never refresh `sessions.last_used_at`.
- **CSRF**: the whole mux sits behind `http.CrossOriginProtection` (Sec-Fetch-Site/Origin; `WEAVE_BASE_URL` is a trusted origin). Requests without browser headers (CLI, agents) pass. No state-changing GETs: logout and `card.next` (claiming) are POST.
- **Request limits**: bodies are capped in `ops.Bind` (2 MiB JSON/form; `Op.MaxBody` for uploads/import), non-public ops authorize before reading the body, multipart memory is 1 MiB, `http.Server.IdleTimeout` 120s (no global `WriteTimeout`: SSE). Text caps: card name 1000, description 200 KB, list/board/label names 255.
- **Images**: `internal/imgguard` reads the header first, rejects > 40 Mpixel and bounds concurrent decodes. Recurrence rules are bounded (interval <= 1000, count <= 10000, constant-time `nextDue`).
- **Secrets**: webhook secrets and access tokens are write-only (`hasSecret`/`hasAccessToken`); events, the activity log and webhook payloads never carry them or notification-service URLs. `WEAVE_SECRET_KEY` signs OIDC state; it does not encrypt the database (protect the volume and backups).
- **Response headers**: `nosniff`, `Referrer-Policy: same-origin` (`no-referrer` on `/share/`, `/public/`), `X-Frame-Options: DENY`, a restrictive `Permissions-Policy`, `Cache-Control: private` on HTML, and a real **Content-Security-Policy**: `default-src 'none'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; media-src/font-src/connect-src 'self'; form-action 'self'; base-uri 'none'; object-src 'none'; frame-ancestors 'none'` (`WEAVE_CSP=enforce|report-only|off`). Consequences for contributors: no inline `<script>`, `on*=` handlers, `javascript:` URLs, `hx-on`, `hx-vals='js:...'` or `hx-trigger` filter expressions (htmx runs with `allowEval=false`); use `data-*` attributes plus the delegated listeners in `static/weave.js`, and put scripts in `/static` (`theme-init.js` runs in `<head>` before first paint). `internal/web/csp_lint_test.go` enforces this. Handlers may override the policy: downloads, share/logo pages send a `sandbox` policy and the export print view allows exactly one inline script by hash (`notify/export.go`). `scripts/csp-smoke.mjs` walks every page in Chromium and fails on any violation (optional, not part of `go test`). htmx is vendored (2.0.11) with its history cache disabled.
- **Abuse limits** (all generous, env-tunable, `0` = off; see README): per-principal token bucket (`WEAVE_RATE_LIMIT`, burst `WEAVE_RATE_BURST`) keyed by a hash of the API key/session cookie (client IP when anonymous; an optional per-IP ceiling `WEAVE_RATE_LIMIT_IP` is off by default because users share IPs), stricter buckets for search, exports/import/service tests and sign-in; `429` + `Retry-After`. SSE, static and `/healthz` are exempt. At most `WEAVE_MAX_STREAMS_PER_USER` live streams per user (released on disconnect). Upload quota per user `WEAVE_USER_STORAGE_MB` (sum of `attachments.size` by uploader, checked in `attachment.create`). Tests: `internal/server/limits_test.go`, `internal/domain/cardextras/quota_test.go`.
- **Notification destinations (SSRF)**: user and board notification services point the server at a URL of the creator's choosing, so `notify/ssrf.go` refuses loopback, link-local (incl. cloud metadata 169.254.169.254, fd00:ec2::254), unspecified and metadata host names, both when a service is saved and, with a fresh DNS lookup of every returned address, right before each send. RFC 1918 stays allowed (self-hosted ntfy/gotify) unless `WEAVE_NOTIFY_BLOCK_PRIVATE=true`; `WEAVE_NOTIFY_ALLOW_HOSTS` overrides blocks. Failures reach users only as `could not deliver: destination unreachable or not allowed` (detail goes to the server log). Residual risk: shoutrrr dials by itself, so DNS rebinding between our lookup and its connection or a redirect to a blocked address is not prevented.
- **Directory privacy**: guests and workers only see users and groups that share a board with them (`user.list/get`, `group.list/get`, `auth/zz_visibility.go`); everyone else keeps the full directory. The board settings page and fragments are for members/managers; viewers of a public board are sent back to the board (`authz.IsBoardMember`).
- **CLI**: config dir 0700/files 0600, schema cache 0600 (no /tmp fallback), http:// warning for non-private hosts, redirects never leave the host with a token or downgrade to http, 64 MiB response cap, control characters stripped from table/text output, handler stderr tails are redacted and capped before becoming comments.
- **Agents**: card content is untrusted data (see `docs/AGENTS.md`, "Security: treat card content as untrusted data").
- **Container**: distroless (debian13) nonroot, read-only rootfs with a `/tmp` tmpfs, all capabilities dropped, `no-new-privileges`.
